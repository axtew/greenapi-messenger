### Решение по открытому пункту 1: удаление отредактированного сообщения

**Вывод: текущего сопоставления хватает для пути через историю, `code`-находки нет.** Остаточный риск есть, но он не внесён этим заходом. Он сидит в сопоставлении `replacesId = editedMessageId || deletedMessageId`, которое задано планом (`plan.md:167`, Phase 2). Закрывать его — поправкой плана по решению владельца (правило ниже).

**Почему хватает.** Заход не меняет набор убираемых записей:
- `replacedIds` в `mergeMessages` (`src/api/cache/messages.cache.ts:44-46`) строится так же, как в Phase 7: по всему объединению, включая записи удаления.
- Убран только фильтр `!isDeleted` (`:48`).
- Итог: видимое сейчас = видимое в Phase 7 + сами записи удаления, на которые никто не ссылается. Изменение строго монотонно.

Владелец проверил руками сборку Phase 7 (`EXECUTION.md:106`): удалённое отредактированное сообщение исчезло полностью. Значит, запись правки была скрыта ссылкой из какой-то записи. В Phase 7 лента собиралась только из `getChatHistory` + `mergeMessages`, уведомлений ещё нет. Тот же набор записей сейчас даст в ленте ровно одну заглушку. По времени это, скорее всего, то самое событие. Живая пара: правка `1791265448`, через 14 с удаление `1791265462`, обе сегодня, после ревью Phase 7, которое предложило такую проверку. Наблюдение владельца исключает вариант, при котором `editedMessageId` записи удаления указывает на тот же оригинал, что и `editedMessageId` записи правки. Тогда правка осталась бы видимой и в Phase 7. Остаются два варианта:
- (а) `editedMessageId` записи удаления = `idMessage` записи правки, и цепочка гасится существующим правилом;
- (б) сервер при удалении сам убирает запись правки из истории.

При обоих текущий код показывает только заглушку. Цепочки «правка правки» тоже уже покрыты: `replacedIds` считается до фильтра, поэтому промежуточные версии гаснут, даже если гаснет их потомок.

**Где реальный остаточный риск.** Два случая, оба шире пути «история после перезагрузки»:
1. **Оригинал из кэша сессии.** Сервис выбрасывает `deletedMessageId`, если `editedMessageId` непуст (`src/api/services/messages.service.ts:58`). Пример: оригинал M (`id = orig`) уже лежит в кэше ленты с прошлого открытия чата. Кэш в памяти сливается при каждом повторном открытии. Затем приходит запись удаления с `editedMessageId ≠ orig` и `deletedMessageId = orig`. Тогда M со старым текстом остаётся рядом с заглушкой до перезагрузки вкладки. Это реально при варианте (б). С Phase 9 случай станет обычным: оригинал попадает в кэш уведомлением по своему `idMessage`.
2. **«Веер» версий.** Несколько записей ссылаются на одну цель, например все правки указывают на `orig`, а не на предыдущую версию. Правило «убрать запись, на чей `id` ссылаются» гасит цель, но не соседние версии. Это ограничение и правок, и удалений. Оно не новое.

**Минимальное устойчивое правило** (для поправки плана; проще всего вместе с пунктом Phase 9 из поправки (16)): запись удаления гасит каждую неудалённую запись, у которой `id` **или** `replacesId` входит в набор ссылок удаления `{editedMessageId, deletedMessageId}` (непустые). Первое условие убирает оригинал и последнюю версию, второе — все версии того же сообщения. Для этого `IMessage` должен нести обе ссылки удаления, а не одну `replacesId`: например, отдельное поле id удалённого или массив ссылок. Обычное правило `replacedIds` остаётся как есть. Правило безопасно: скрыть оно может только версии удалённого сообщения. Если тип не трогать, есть урезанный вариант в одну строку `mergeMessages`. Он гасит неудалённые записи, чей `replacesId` равен `replacesId` записи удаления, и закрывает «веер», но не случай 1.

**Решающая проверка (один вызов, без секретов).** Один `getChatHistory` по тестовому чату. В вывод — только булевы совпадения для записей с индексами 0 и 1:
- `del.editedMessageId === edit.idMessage`;
- `del.editedMessageId === edit.editedMessageId`;
- `del.deletedMessageId === edit.editedMessageId`;
- совпадают ли `type`.

Если первое `true` — подтверждён вариант (а). Если `type` разный, а совпадений нет, — запись правки к удалению не относится, вариант (б). Параллельный визуальный проход тоже может посмотреть ленту тестового чата. Около времени `1791265448` не должно быть пузыря с текстом правки того же направления, что и заглушка.
