## Summary

Iter-3 закрывает поправку «Phase 3 — added 2026-10-05 (5)»: `GreenApiError.message` теперь собирается из кодов, справочника человекочитаемых причин больше нет. Изменение затрагивает одну строку конструктора и JSDoc класса в `src/api/greenApi/_client.ts`. Формат совпадает с поправкой, токен в `message` попасть не может, правила `cause` не менялись, JSDoc соответствует коду. Остальная фаза одобрена в iter-2 и в этой итерации не менялась.

## Проверено

- **Формат `message`** — `src/api/greenApi/_client.ts:29`: `GREEN-API ${method}: ${kind}` и `` ` ${status}` ``, только если `status !== null`. `kind` и `method` — строковые `enum` (`_types.ts:6–27`), поэтому в строку попадают их значения: `http`, `network`, `invalidResponse`, `rateLimited`, а также имя метода из URL. Результат совпадает с примерами поправки (`GREEN-API getStateInstance: http 401`, `GREEN-API getChats: network`). Отказ в `checkAccount` (`chats.service.ts:33–38`, статус 200) даёт `GREEN-API checkAccount: rateLimited 200` или `GREEN-API checkAccount: invalidResponse 200`, как и описано в отчёте.
- **Токен не может попасть в `message`.** Строка собирается только из `EGreenApiMethod`, `EGreenApiErrorKind` и `number | null`. Ни URL, ни `credentials`, ни текст исходной ошибки в неё не передаются. Тест `api.test.ts:225–245` прогоняет все четыре `kind`, включая сетевой сбой, в тексте которого лежит токен, и проверяет `message` на отсутствие токена. Тест проходит.
- **Правила `cause` не изменились.** Строки 76–98 совпадают с `HEAD`: у сетевого сбоя нет `cause` (комментарий :81), при не-JSON `cause` нет, при ошибке схемы `cause` — `ZodError` (:92–97). Оба комментария по-прежнему соответствуют коду.
- **JSDoc класса** (:10–16) верен. Формат описан точно. Утверждение «тексты для пользователя выбираются по `kind` и `status`, а не по `message`» подтверждается кодом: `_useLoginForm.ts:19–33` выбирает текст по `instanceof`, `kind` и `status`, а `_queryClient.ts:18–30` смотрит только на `status`. Первая строка JSDoc объясняет назначение, следов пайплайна в нём нет.
- **`message` не читается нигде для пользовательского текста.** Grep по `src/` нашёл `.message` только в тесте токена (`api.test.ts:244`). Ни `String(error)`, ни интерполяции ошибки в JSX тоже нет.
- **Устаревших упоминаний нет.** В `src/` и `docs/` не найдены ни `ERROR_REASONS`, ни описание «исчерпывающего выбора причины».
- **Verification** (план, Phase 3: `pnpm lint`, `pnpm build`) я перезапустил сам, плюс `pnpm test`. Все три команды завершились с exit 0, тесты 32/32. Это совпадает с отчётом, команды не подменены.
- **Exports.** Новых экспортов нет: `ERROR_REASONS` был внутренней константой модуля и удалён.

## Notes

- Точный текст `message` ни один тест не фиксирует. Разработчик сам указал это в отчёте как Known issue. Это не блокирует: строка отладочная и пользователю не показывается. Если владелец захочет зафиксировать формат из поправки, хватит одной проверки в существующем тесте `api.test.ts:225–245`, например `expect(errors[0].message).toBe("GREEN-API getChats: http 401")`. Метод и статус там подставить фактические.
- `InstanceNotAuthorizedError` (`session.mutations.ts:8–13`) по-прежнему держит человекочитаемый русский `message`. Поправка касается только `GreenApiError`. Этот текст тоже нигде не показывается, форма выбирает текст по `instanceof`, так что расхождения нет. Отмечаю только для единообразия: владелец может решить, нужно ли менять и его.
