## Решение по открытому вопросу разработчика: `notAuthorized` как строковый литерал

Это **не `code`-замечание**, и `enum` здесь заводить не нужно.

1. **Правило `typing.md:11–16` здесь не применяется.** Оно касается ограниченных наборов значений, которые код сравнивает, по которым различает варианты или которые хранит в состоянии. В этом месте нет ни набора, ни сравнения. Это одна константа внутри отладочной строки. `message` никто не читает, а форма различает ошибки по классу. Строковый `enum` из одного члена, который нигде не сравнивается, получился бы ради формы, а не ради типобезопасности.
2. **`EStateInstance.NOT_AUTHORIZED` был бы ошибкой.** Комментарий к `EStateInstance` (`account.schema.ts:3`) говорит, что это значения, которые проверяет код, а `notAuthorized` код не проверяет. Хуже того, такой член выдавал бы `notAuthorized` за значение поля из API. На деле `checkInstanceAuthorized` возвращает `false` для любого состояния, кроме `authorized`: для `starting`, `blocked` и других. JSDoc класса это прямо оговаривает («или ещё запускается»). В `message` `notAuthorized` стоит на месте `kind` и по смыслу означает вид ошибки (повторяет имя класса), а не полученное `stateInstance`. Для этой роли литерал честнее, чем член enum значений API.
3. **Передавать фактическое `stateInstance` — несоразмерная правка для этой итерации.** Пришлось бы менять контракт сервиса из Phase 2, который уже закоммичен: по плану `checkInstanceAuthorized(credentials)` возвращает `boolean` (`plan.md:357`). Сравнение с `EStateInstance.AUTHORIZED` переехало бы в мутацию, а ради строки, которую пользователь не видит, пришлось бы переписать тест сервиса (`api.test.ts:252–258`). Если владелец захочет видеть в `message` реальное состояние, это поправка плана, а не исправление кода (см. Notes).

## Notes

- **Реальное состояние в `message` (на усмотрение владельца).** Сейчас для инстанса в состоянии `starting` в `message` окажется `GREEN-API getStateInstance: notAuthorized`. Тот, кто будет отлаживать, может принять это за ответ API `notAuthorized`. Пользователь ничего не теряет: текст ошибки один для всех таких состояний (`plan.md:418`). Если владелец захочет точнее, понадобится поправка плана примерно такого вида. Сервис возвращает `stateInstance` (или бросает ошибку сам). Мутация сравнивает его с `EStateInstance.AUTHORIZED` и передаёт полученное значение в `InstanceNotAuthorizedError(stateInstance)`. `message` тогда равен `GREEN-API getStateInstance: <stateInstance>`, и литерала не остаётся. Это затронет `account.service.ts`, `session.mutations.ts`, тест сервиса и строку 357 плана. Без этой поправки текущий код корректен.
- Точный `message` у `InstanceNotAuthorizedError` тест не фиксирует. Владелец просил закрепить только формат `GreenApiError`, поэтому это не пробел.
