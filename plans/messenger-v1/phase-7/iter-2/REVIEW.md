## Notes

**`setQueryData` внутри `queryFn` с возвратом тех же данных — разбор (TanStack Query 5.104.1, `query-core/build/modern/query.js`).** Если коротко: всё корректно, у паттерна есть прецедент в репозитории (`syncChats`), блокирующих проблем нет.
- *Двойная запись и structural sharing.* `updateMessages` вызывает `setQueryData` → `query.setData(next, { manual: true })` → `replaceEqualDeep(prev, next)`, и в `state.data` попадает структурно разделённая копия. Поэтому тест и сравнивает через `toEqual`, а не `toBe`, и это правильно. Затем ретрайер вызывает `this.setData(returned)` (стр. 392), и `replaceEqualDeep(state.data, next)` на глубоко равных данных возвращает уже сохранённую ссылку. Ссылка на `data` у наблюдателя между двумя записями не меняется, так что лишних пересчётов по `data` нет. `dataUpdateCount` растёт на 2 вместо 1, но ничего в проекте от него не зависит.
- *Ре-рендеры.* Ручная запись диспатчит `success` с `manual: true`, а `fetchStatus` остаётся `fetching` (стр. 442: `...!action.manual && { fetchStatus: "idle" }`). Если история что-то меняет, `MessageList` (следит за `data`, `isError`, `isFetching`) рендерится два раза: сначала с новыми данными при `isFetching: true`, затем при `isFetching: false` с той же `data`. Раньше рендер был один. Если история ничего не меняет, `replaceEqualDeep` возвращает прежнюю ссылку, отслеживаемые поля не меняются и лишнего рендера нет. На логику это не влияет: `isFailed` требует `messages === undefined`, а `useAutoScroll` срабатывает на рост числа сообщений, и это случается в первом из двух рендеров, во втором нет. На 100 сообщениях цена — один лишний `buildListItems`, пренебрежимо мало.
- *Гонка с собственной записью результата.* Между `return next` и `setData(returned)` ретрайера проходит несколько микротасков (цепочка промисов retryer/fetch). Если в это окно другой код запишет ключ через `updateMessages` (в Phase 8/9 это `onMutate` и `applyNotification`), запись результата затрёт её значением `next`. Регрессией это не является: у кода iter-1 (`getQueryData` → `return`) окно было то же, у `syncChats` — тоже. На практике оно недостижимо: ответы `fetch` и тики poller'а приходят макротасками, а в окно попадают только микротаски, уже стоящие в очереди. Отмечаю это для Phase 9: если `applyNotification` когда-нибудь будет вызываться из микротаска, который продолжает тот же `await`, что и `queryFn`, этот случай нужно перепроверить.
- *Отмена (`cancelRefetch` / revert).* При ручной записи `#revertState` становится состоянием после этой записи (стр. 448), поэтому откат не вернёт кэш к данным до слияния. Если fetch отменён, его `setQueryData` уже выполнился, но результат — идемпотентное слияние, не регрессия.

**Мелочь, не блокирует:** название теста «в кэш сохраняется тот же список, что возвращается» при проверке через `toEqual` по сути означает «равный список». Можно уточнить формулировку, если тест будут трогать.

**Без изменений с iter-1:** открытые вопросы из Notes iter-1 по-прежнему на усмотрение владельца и для этой итерации не блокируют. Это автопрокрутка только на рост списка, невидимая ошибка повторного запроса, `refetch` из компонента против формулировки в `architecture.md`, inline-форма `{ today; yesterday }` и непроверенный на живом API `deletedMessageId` для удаления уже отредактированного сообщения. `.playwright-mcp/` в рабочем дереве нет.
