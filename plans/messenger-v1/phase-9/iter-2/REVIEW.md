## Notes (optional)

- **`lastReceiptId` переживает успешное удаление — на усмотрение владельца.** Поправка (20) требует «помнить `receiptId` последнего обработанного», и код делает именно это. Но пропуск нужен только пока удаление не прошло. По `brainstorm.md:139` и `phase-9/iter-1/VISUAL.md:15` (`receiptId` 20, 21 после пустой очереди) счётчик сквозной и при опустевшей очереди не сбрасывается, поэтому сейчас риска нет. Сбрасывается ли он при очистке очереди или перезапуске инстанса, неизвестно. Если сбрасывается и новое уведомление получит ровно тот же номер, что последнее обработанное, оно будет удалено **без обработки**, то есть входящее потеряется молча. Дешёвая страховка: после успешного `deleteNotification` обнулять `lastReceiptId`. Тогда пропуск срабатывает только для уведомления, удаление которого не прошло. Тест на повтор при этом остаётся зелёным.
- **Защиты от мгновенного пустого ответа нет (так было и раньше).** `null` и 408 идут без паузы. Это верно, пока сервер держит запрос: по `VISUAL.md:66` 408 приходит через 11–26 с. Если GREEN-API начнёт отвечать 408 или `200 null` сразу, цикл забросает API запросами. Сейчас не воспроизводится; кандидат в `BACKLOG.md`, если владелец захочет минимальную паузу на коротких пустых циклах.
- **Консоль Chrome и 408.** По `VISUAL.md:76` Chrome пишет ответ 408 в консоль DevTools вместе с URL запроса, а в URL лежит `apiTokenInstance`. Теперь 408 — обычный пустой цикл, так что такая строка будет почти на каждом цикле. Из JS это не подавить, а токен в пути задан форматом API GREEN-API. Это не находка по коду, но владельцу стоит знать: скриншот или лог консоли открытого приложения содержит токен. Пайплайн уже обходит это правилом профиля (консоль не читается).
