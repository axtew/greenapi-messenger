## Phase goal

Phase 5 — список чатов и синхронизация с сервером. Левая панель показывает чаты из localStorage сразу и при входе обновляет их с сервера: имя, аватар, последнее сообщение, время, бейдж непрочитанных.
Условие остановки: после входа в новом браузере тестовый чат появляется с именем, аватаром и последним сообщением; после перезагрузки — сразу, без `getContactInfo`.

## Plan gap

**Опции `useChatsQuery` из плана не запускают синхронизацию ни разу.** Phase 5, п. 2 задаёт три опции:

- `initialData: () => readStoredChats(id)`;
- `initialDataUpdatedAt: 0`;
- `staleTime: Infinity`.

План ожидает от них «синхронизация стартует при монтировании, повторной в сессии нет». TanStack Query v5 (`@tanstack/query-core@5.104.1`) ведёт себя иначе.

**Почему так.** По исходникам `query.ts`, `isStaleByTime` равен `!timeUntilStale(dataUpdatedAt, staleTime)`. Функция `timeUntilStale` (`utils.ts`) считает `max(updatedAt + staleTime - Date.now(), 0)`. При `updatedAt = 0` и `staleTime = Infinity` это даёт `Infinity`, поэтому данные **никогда не stale**.

`initialData` всегда определён: `readStoredChats` отдаёт `[]` даже при пустом хранилище. Значит, `shouldFetchOnMount` (`queryObserver.ts`) идёт по ветке «данные есть». Там `refetchOnMount` срабатывает только для stale-данных, и `queryFn` не вызывается.

**Проверка.** Запустил `QueryObserver` из установленного `query-core` в Node; временный скрипт лежал в scratchpad и уже удалён.

| Опции | Вызовов `queryFn` | Данные |
|---|---|---|
| по плану, хранилище пусто (`initialData → []`) | **0** | `[]` |
| по плану, в хранилище есть чат | **0** | сохранённые |
| `staleTime: 0` (для сравнения) | 1 | с сервера |

**К чему это приводит.** В новом браузере список остаётся пустым навсегда: на экране вечный `sidebar.emptyTitle`, запросов `getChats` нет. Условие остановки фазы и проверку `list_synced` выполнить нельзя.

Это расхождение плана с реальным поведением библиотеки. По `AGENTS.md` («Расхождение плана с реальностью — остановиться и сообщить, не обходить») и по указанию в задаче я остановился до правок кода.

## Recommended fix

1. **Рекомендую.** `staleTime` функцией: `(query) => (query.state.dataUpdatedAt === 0 ? 0 : Infinity)`, `initialDataUpdatedAt: 0` оставить. Тогда данные из хранилища stale до первой успешной синхронизации, а после неё — `Infinity`, и повторной синхронизации в сессии нет. Проверено тем же скриптом:
   - первый наблюдатель — 1 вызов `queryFn`;
   - второй наблюдатель после успеха — 0 вызовов.

   У этого варианта есть следствие. Если синхронизация закончилась ошибкой, `dataUpdatedAt` остаётся `0`. Тогда следующий новый наблюдатель (например, `_useChatPage` в Phase 6) запустит её ещё раз. Для повторной попытки после сбоя это скорее плюс.
2. **Альтернатива.** `refetchOnMount: "always"` в опциях `useChatsQuery`, `staleTime: Infinity` оставить. Хуже: каждый новый потребитель хука (Phase 6 — экран чата и шапка) при монтировании заново запускал бы полную синхронизацию — `getChats` и `getChatHistory` × 10.
