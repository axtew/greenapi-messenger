# Структура — размещение, экспорты, семейства типов

## Размещение — одна лестница для всего вынесенного

Типы, хелперы, константы, хуки и подкомпоненты подчиняются одному правилу: **сущность живёт на самом низком уровне, который покрывает всех её
текущих потребителей, и поднимается выше только при появлении реального второго потребителя.** Ничего не выносится в общее «на вырост».

Лестница снизу вверх:

1. **Внутри файла, который её использует** — пока файл укладывается в лимиты ниже.
2. **Рядом с компонентом, с подчёркиванием** — `_types.ts`, `_helpers.ts`, `_constants.ts`, `_use<Name>.ts`, `_<Sub>.tsx`.
3. **Корень самого компонента** — когда второй потребитель появился внутри его `_internal/`, общая сущность поднимается:
   `SomeComponent/_internal/SomeSub/_types.ts` → `SomeComponent/_types.ts`.
4. **Корень группы** — когда сущность нужна нескольким соседним компонентам одной группы, она переезжает в папку группы (например, `_internal/` страницы).
5. **Глобально** — `src/types/`, `src/utils/helpers/`, `src/components/` — только когда потребители есть в двух и более фичах или страницах.
   Исключение — обёртки над встроенными API и общие алиасы типов: они в общем слое с первого использования (раздел «Общий слой»).

**Выход из файла (шаг 1 → 2).** Тип остаётся в файле, пока в нём объявлено не больше одного `type` / `interface` / `enum` **и** в нём меньше 10 полей.
Триггер переезда: **≥ 2 объявления или одно объявление с ≥ 10 полями.** Как только появился `_types.ts`, в нём живут **все** локальные типы компонента,
включая тип пропсов, — раскладывать типы между TSX и `_types.ts` это правило и запрещает.

**Глобальные типы** — в `src/types/`, по файлу на домен или тему: `chats.types.ts`, `messages.types.ts`, `common.types.ts`, `i18n.types.ts`.
Группировка — **по домену, которому принадлежит понятие**, а не по тому, откуда оно пришло. Папка «типы API» выглядит аккуратно ровно до момента,
когда форма ответа становится сущностью, нужной и форме ввода, — дальше всё стекается в одно место, чтобы избежать циклических импортов,
потому что «из API или нет» не свойство типа. Домен — свойство. Разросшийся домен становится папкой — та же лестница уровнем выше.

**Обработчики — тоже.** Обработчик, который нужен ровно одному дочернему компоненту, объявляется **в нём**, а не поднимается в хук фичи
и не прокидывается через пропсы. Хук фичи «на всё, что фича трогает» выглядит единой точкой входа, но тянет логику, у которой один потребитель-лист:
хук распухает, лист превращается в проводку пропсов. В хуке фичи — то, что нужно двум и более детям или самому корню фичи.

**Дисциплина экспорта** действует на каждой ступени лестницы — см. раздел ниже.

## Общий слой — сначала он, потом встроенный API

Общий слой проекта — `src/utils/` (обёртки над браузерными и стандартными API, общие хелперы) и `src/types/common.types.ts` (общие алиасы типов).
Перед прямым вызовом встроенного API (`Object.entries` / `keys` / `values` / `fromEntries`, `localStorage` / `sessionStorage`, `document.cookie` и т. п.)
и перед объявлением алиаса над типом React или TS (`Dispatch<SetStateAction<T>>` и т. п.) — перечислить эти места (имя файла говорит, что в нём)
и взять готовое. Прямой вызов при наличии обёртки — находка `code`.

**Новая обёртка над встроенным API или общий алиас** сразу кладётся в общий слой, а не поднимается по лестнице: её назначение — заменить
встроенный вызов везде, значит она общая по определению, а не «на вырост». JSDoc обёртки говорит, **что она заменяет и почему**
(«вместо `Object.entries`: ключи сохраняют тип объекта»). В семейство добавляется то, что вызывается сейчас, а не все обёртки заранее.

## Дисциплина экспорта — экспорт нужен импортёру, а не на всякий случай

`export` — заявление, что сущность входит в публичный контракт модуля. Он добавляется в том же изменении, что и импортирующий код, — никогда заранее.
Правило действует на трёх уровнях, и проверка везде одна: **найти импортёра поиском — ноль импортёров означает отсутствие экспорта.**

- **Символ в файле** — тип, константа или функция, используемые только внутри своего файла, не экспортируются. `_types.ts` не исключение:
  форма, на которую ссылается только другой тип того же файла, `export` не требует. (Неэкспортированный интерфейс всё равно доступен структурно
  через экспортированный тип, который на него ссылается; экспорт нужен, только когда потребителю надо _назвать_ его — например, в своей сигнатуре.)
- **Barrel (`index.ts`)** — строка появляется, когда сущность импортирует потребитель снаружи папки. Символы, нужные только соседям внутри папки,
  импортируются напрямую из `./_module`, не через barrel.
- **Уровень модуля** — то же правило уровнем выше: хелпер, общий для двух файлов папки, экспортируется из своего файла, а не переезжает в общее место.

«Следующим фазам наверняка понадобится» — не причина: когда понадобится, добавить строку — одна правка, и она придёт вместе с импортёром.
Если фаза сознательно готовит символ для конкретной следующей фазы, это решается в плане (заготовка, ниже), а не догадкой в коде.
Отложенная чистка («уберём лишние экспорты в конце») не случается: к концу никто не помнит, какие экспорты были спекулятивными.

Для ревьюера то же: экспорт без импортёра вне своего модуля и без одного из исключений ниже — находка `code`, а не заметка на будущую фазу.

Исключений два — у обоих обоснование записано, а не подразумевается.

**Заготовка под будущую фазу.** Экспорт без импортёра допустим, если план объявляет его заготовкой: у фазы есть раздел
`**Provisioned for later phases**` с таблицей `символ | фаза-потребитель | как используется`, и фаза-потребитель упоминает этот символ в своих деталях.
Разработчик перечисляет заготовки в отчёте отдельно. Ревьюер проверяет: (1) каждый экспорт без импортёра есть в этом разделе текущей фазы;
(2) названная фаза-потребитель действительно использует символ по тексту плана; (3) экспортов без импортёра сверх списка нет; (4) при ревью
фазы-потребителя у заготовки появился импортёр — если нет (план изменился), это находка: убрать экспорт или поправить план.
Без записи в плане — по-прежнему находка `code`.

**Символ, завершающий контракт, который определяет сама фаза.** Когда фаза выносит существующее поведение из структуры
(например, заменяет поле-функцию в интерфейсе на данные плюс свободную функцию рядом), у свободной функции до следующей фазы нет импортёра —
но без экспорта передаётся структура, смысл которой нигде не описан. Это перенесённая реализация, а не «вдруг пригодится». Разработчик называет символ
и причину в отчёте; ревьюер проверяет обоснование, а не только считает импортёров. Экспорт без импортёра и без такого обоснования — находка `code`.

## Расширять существующее семейство, а не открывать параллельное

Прежде чем вводить новый тип или форму конфига, найти существующее семейство того же класса и добавить в него член: набор строковых enum,
сведённых в общий union и сужаемых guard-функциями проверки принадлежности; реестр однотипных записей; набор параллельных констант.
Новая форма рядом с таким семейством (объект там, где соседи — члены enum; второй список опций там, где один уже есть) заставляет каждого
потребителя обрабатывать две формы и трогать файлы, которые расширение семейства оставило бы нетронутыми.

Новая форма оправдана, только если у сущности есть поля сверх идентификатора, по которому устроено семейство.

Если план предлагает параллельную форму, а семейство уже есть: следовать семейству и назвать расхождение в отчёте — не делать молча ни то, ни другое.
Если форма из плана несущая (на неё опираются следующие фазы) — остановиться и спросить, а не решать в одиночку.
