# Архитектура

SPA без собственного бэкенда: браузер ходит в GREEN-API напрямую (API отдаёт `Access-Control-Allow-Origin: *`),
сборка — статика на Cloudflare Workers Static Assets.

## Источник истины по API

Документация Telegram-продукта GREEN-API: https://green-api.com/telegram/docs/api/ — формы запросов, ответов и уведомлений
берутся оттуда, а не выводятся из места вызова. Сводка по используемым методам и проверенные факты — в `plans/messenger-v1/brainstorm.md`.
Каждый запрос: `{apiUrl}/waInstance{idInstance}/{method}/{apiTokenInstance}`.

## Путь данных — единственный

```
компонент → хук TanStack Query (query / mutation) → сервис → клиент GREEN-API → fetch
```

- **Компонент не вызывает `fetch` и клиент GREEN-API.** Чтение — query-хук, запись — mutation-хук.
- **Только сервисы решают, какой метод GREEN-API вызвать и с каким телом.** Клиент знает хост, форму URL и набор имён методов
  (`enum`, которым типизирован запрос), но сам методы не выбирает. Сервисы — plain-функции по доменам, не классы.
  Сервис — граница типов: отдаёт сущности проекта (`src/types/<domain>.types.ts`), сырые формы ответов API наружу не выходят.
- **Ключи запросов** — в одном модуле на домен; инвалидация по ключу, без ручных refetch из компонентов.

## Получение сообщений — poller

Получение — отдельный TS-модуль вне React: цикл long-polling `receiveNotification` → обработка → `deleteNotification`.
Инварианты (нарушение — дефект, даже если «работает»):

- **Удаляется каждое полученное уведомление**, включая нетекстовые и служебные — иначе очередь встаёт на нём навсегда.
  Удаление — после обработки, не до.
- **Один потребитель очереди:** старт идемпотентен (StrictMode монтирует эффекты дважды), между вкладками — лидер через Web Locks.
  Выход из аккаунта прерывает цикл (AbortController).
- **Уведомления — внешние нетипизированные данные:** разбираются zod-схемой по `typeWebhook` на границе; дальше идут только типы проекта.
- **Poller пишет в кэш TanStack Query** (`setQueryData`) — второго хранилища сообщений нет.
- **Дедупликация по `idMessage`** между историей, очередью, optimistic-сообщением и эхом `outgoingAPIMessageReceived`.
- Ошибки сети и 429 — backoff, а не плотный цикл повторов.

## Чаты и chatId

- **chatId — числовая строка из ответа `checkAccount`** (или из `senderData.chatId` входящего). Формат `номер@c.us` не используется:
  он не совпадает с chatId входящих и тратит отдельный слот квоты тарифа.
- Входящее из неизвестного чата создаёт чат в списке.
- Лимиты тарифа «Разработчик» в логику не закладываются — только понятная ошибка на ответ 466 / уведомление `quotaExceeded`.
